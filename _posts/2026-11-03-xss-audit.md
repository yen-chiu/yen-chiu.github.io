前几天给博客加了个「写作台」——一个纯前端的 Markdown 编辑器，直接调 GitHub Contents API 提交文章。
它把 Fine-grained PAT 存在 `localStorage` 里，编辑时用 `marked` 渲染预览。

功能跑通之后我做了一件之前没做过的事：**让安全审计专家只读审查这套代码**。
结果它翻出一个真漏洞，而我原本以为那部分「已经防住了」。

## 一、漏洞长什么样

预览是用 `marked` 把 Markdown 转成 HTML，再塞进 `innerHTML`，中间有一层 `sanitize()` 过滤危险标签和属性。
过滤 URL 用的是**黑名单**：遇到 `javascript:` 就丢掉这个 `href`。

审计给出的 payload 是这样一行 Markdown：

```markdown
<a href="java&#9;script:window.__xss=1">click</a>
```

我没当回事——`java&#9;script:` 又不是 `javascript:`，黑名单匹配不上。
直到用 Puppeteer 在真实浏览器里点了一下：**`window.__xss` 变成了 1**。

原因很简单也很经典：`&#9;` 是 Tab 的 HTML 实体，浏览器解析完 HTML 属性后，
`href` 的值是 `java<Tab>script:...`；而浏览器在解析 URL 时会**剥离 Tab 和换行**，
最终执行的就是 `javascript:window.__xss=1`。我的黑名单只检查了字符串形态，没检查「浏览器最终会怎么理解它」。

同类变形还有换行（`&#10;`）、回车（`&#13;`）、前导空白、大小写混写。
更糟的是 `img` 的 `srcset`：它是一串用逗号分隔的候选，整串丢给黑名单判断也能被绕过。

危害不是弹个框：这个页面里存着 PAT，脚本可以读 `localStorage` 把它发出去。

## 二、修法：从黑名单改成白名单

原来的逻辑是「看起来像 XSS 就拦」，现在改成「必须是已知安全的形式才放行」，顺序很重要：

```js
function isSafeUrl(value) {
  // 1. 先把所有控制字符和不可见空白剥掉，再判断
  const v = String(value).replace(
    /[\u0000-\u0020\u007f\u00a0\u2000-\u200f\u2028\u2029\ufeff]+/g, ''
  );
  if (!v) return true;                                  // 空属性无害
  if (/^[\\/]{2}/.test(v)) return false;                // 协议相对 //evil.com、\\evil.com 不放行
  if (/^(#|\/|\?|\.{1,2}\/)/.test(v)) return true;      // 锚点 / 站内路径 / 相对路径
  if (!/^[a-z][a-z0-9+.-]*:/i.test(v)) return true;     // 没写协议，按相对路径处理
  return SAFE_SCHEME.test(v);                           // 只放行 http(s)/mailto/tel
}
```

几个容易漏的点：

- **先剥控制字符再判断**，而不是判断完再剥。否则「判断时看到的」和「浏览器看到的」不是同一个字符串
- `//evil.com` 是协议相对 URL，会被当外链跳转，必须显式拒绝
- `srcset` 要**逐个候选**校验，含 `data:` 的整串丢弃（data URL 自带逗号，会破坏逗号分隔的解析）
- 剥离 `id` / `name`（防 DOM clobbering 和 UI 钓鱼）、`ping`（点击外发信标）、所有 `on*`

同时把任务列表的 `<input type=checkbox>` 换成 `☑` / `☐` 文本——
预览里本来也不该出现可点击的控件。

## 三、修完之后，再评审一次

我又让代码评审专家复查这次的改动。它抓到一个**我自己引入的回归**：

> OAuth 令牌过期（约 8 小时）时，`onAuthExpired()` 复用了 `clearConfig()`，
> 而 `clearConfig()` 里顺手把所有本地草稿删了。

也就是说：写到一半的文章，因为令牌到期被**静默清空**。
修法是把 `purgeDrafts()` 拆出来，只在用户显式点「退出登录」时调用。

如果只做「修漏洞」而不做「评审修复」，这个回归就会悄悄上线，而且丢的是别人的稿子。

## 四、顺手收紧的几处

| 问题 | 处理 |
| --- | --- |
| `refresh_token` 存了却从不用 | 不再持久化，加载时顺手擦掉旧值；Worker 里 `/refresh` 端点直接删掉 |
| Worker 只有 Origin 白名单，curl 可伪造 | 加按 IP 的滑动窗口限流 + `Retry-After` |
| `/admin/` 的 `robots` meta 写在 `<body>` 里 | 移到 `<head>`（写在 body 里浏览器照样索引） |
| 写作台和博客同源，却加载 gtag / jsdelivr | 写作台跳过所有第三方脚本，再加 CSP |
| PWA 会缓存 `/admin/` | `pwa.cache.deny_paths` 排除 |

## 五、测试入库

漏洞最怕的不是修不完，是**修完又悄悄回来**。所以这些用例全部进了仓库：

```text
tools/test/sanitize-xss.mjs   13/13   含 java&#9;script: / srcset / //evil.com
tools/test/ui-smoke.mjs        2/2    任务列表渲染、令牌过期不清草稿
Worker 单元测试               10/10   限流、CORS、/refresh 已下线
写作台 E2E（令牌 / 设备码）   16/16 · 11/11
```

修复前后各跑一遍最关键：**修之前 13 条里有 2 条真的能执行**，修之后线上同样 13/13 全过。

## 六、三条教训

1. **黑名单永远在追着攻击者跑**。凡是「安全字符集合是有限已知的」场景（URL 协议、文件类型、SQL 关键字），都应该用白名单
2. **判断之前先做规范化**。控制字符、Unicode 空白、HTML 实体、大小写——这些「看起来一样其实不一样」的地方，是绕过的主要来源
3. **修复本身也要被评审**。这次真正危险的其实不是漏洞，而是我修漏洞时顺手引入的丢稿回归

顺带说一句：这套「召唤专家 → 我自己复现 → 修 → 再评审」的流程，
比读十篇最佳实践有用得多。因为读来的东西你会觉得「我懂」，
而自己写的东西被真真切切打穿一次，就再也忘不掉了。
