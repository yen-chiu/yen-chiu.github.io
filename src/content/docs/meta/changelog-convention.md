## 先看事实：三代站点

版本号不是凭空定的，先看仓库里真实发生过什么（截至 2026-11-19）：

| 代次 | 站点 | 时间 | 提交 |
| --- | --- | --- | --- |
| G1 | blog-v1 · Jekyll/huxpro（存档） | 2017-02 – 2019-09 | 550 |
| G2 | yenchiu.com · Jekyll/Chirpy | 2019-09 – 2026-11 | 2,099 |
| G3 | 新站 · Astro/Iris（预览） | 2024-07 – 现在 | 862 |

子站：Manual 1,575 次提交（2017-03 起）、Chat 114 次（2024-11 起）、Folio 4 次（2026-11 起）。G2 仓库有 92 个标签，从 `v2.0` 走到 `v7.6.0`。

两条关键事实决定了编号方式：

1. **G2 已经把 `v1`–`v7` 号段用掉了**（2020-09 的 `v2.0` 到 2025-10 的 `v7.4.1`），新站再从头数 `v1.0` 会和老标签撞车，看历史的人分不清是哪一个 `v1.0`。
2. **2026-11 起标签已经变成日期**：`pre-auto-2026-11-03`、`2026-11-04`、`2026-11-04.1` —— 仓库自己已经走到了日历版本。

## 标准里怎么选

- [Semantic Versioning 2.0.0](https://semver.org/lang/zh-CN/)：`MAJOR.MINOR.PATCH`，前提是「有对外 API，且不兼容的改动能被消费者感知」。博客没有 API 消费者，`MAJOR` 只能靠人拍脑袋定义「什么算不兼容」——G2 时代 `v2 → v7` 的进位基本就是「感觉该升了」，这正是 SemVer 在站点上的失效点。
- [Calendar Versioning](https://calver.org/)：用日期当版本，适合「持续交付、用户只关心新旧」的产物（Ubuntu 24.04、PyCharm 2024.1）。站点每天在改，日期天然可比、可查、不会撞号。
- [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)：不规定编号，只规定**条目怎么写** —— 按 新增 / 调整 / 修复 / 移除 / 弃用 / 安全 分类，日期真实，人写得出来也看得懂。

结合实际情况，本站取 CalVer 编号 + Keep a Changelog 的写法。

## 版本号

- 格式 **`vYYYY.MM.DD`**，例如 `v2026.11.19`；同一天发布第二次用 `v2026.11.19.1`，与仓库 tag 的 `2026-11-04.1` 一致。
- 仓库打 tag 用连字符形式 `2026-11-19`，页面上显示成点分形式 `v2026.11.19`。
- **一天最多一条**：当天改多少处，都收进这一条的 `items` 里逐项列出；当天没改动就没有新版本。
- 旧号段 `v2.0`–`v7.6.0` 原地保留，不重排、不回填到新页 —— 它们是 G2 的历史。
- 换代次（换架构、换新站）不进位版本号，而是用 `gen` 字段标记，页面显示「第 3 代」。

## 代次

| gen | 含义 |
| --- | --- |
| 1 | blog-v1 时代（Jekyll · huxpro，2017-02 – 2019-09） |
| 2 | yenchiu.com 时代（Jekyll · Chirpy，2019-09 – 2026-11） |
| 3 | Astro 新站（2024-07 起预览，正式切换后继续用 3） |

换代次时只改 `gen`，版本号继续按日期走 —— 「哪一天」和「哪一代」是两个维度，混在一个数字里迟早要对不上。

## 条目怎么写

对齐 Keep a Changelog 的分类，中文落成：

| 本站 kind | 对应 | 用在哪 |
| --- | --- | --- |
| `feature` | Added / 新增 | 新功能、新页面 |
| `fix` | Fixed / 修复 | 修 bug、修错字级问题 |
| `style` | Changed / 调整 | 排版、配色、交互手感 |
| `infra` | 本站扩展 | 构建、部署、迁移、体积优化 |
| `docs` | Changed / 文档 | 文档与规则本身 |
| `content` | — | **已停用**：文章发布不记日志 |

一条记录长这样：

```json
{
  "version": "2026.11.19",
  "gen": 3,
  "date": "2026-11-19",
  "title": "更新日志独立成页，版本号定下规则",
  "summary": "一句话说清这一天做了什么",
  "items": [
    { "kind": "feature", "scope": "主站", "title": "更新日志独立成页", "note": "一句细节" }
  ]
}
```

页面上 `items` 每条行高固定，超过 3 条在框内滚动，一天改得再多也不会把页面撑长。

## 日期

- `date` 取这一天**最后一次真实提交**的日期（`Asia/Shanghai`，`YYYY-MM-DD`），不按发稿日补、不按印象填。
- 跨零点的改动记在提交发生的那一天。
- 回填方式：`git log --since=… --pretty='%h %ad %s' --date=iso-strict`，用提交时间校准。

## 流程

1. 改完并提交站点改动；
2. `git log` 取当天的最后一次提交时间；
3. 今天已有版本就往那一条的 `items` 追加；没有则新建一条，`version` 写当天的 `YYYY.MM.DD`；
4. 跑 `npm run build`，确认 `/changelog` 与关于页的最近三条都正常；
5. 提交信息用 `docs(changelog): v2026.11.19 一句话`。

## 为什么不用 SemVer

不是 SemVer 不好，是它在这儿没有可测量的对象：站点没有对外 API，读者也不按版本号写代码。仓库里 `v2.0 → v7.6.0` 的进位更多是「这次改动大」的主观判断，回看时说不清 `v5.0` 到底「破坏」了什么。日期版本没有这个问题 —— `v2026.11.04` 就是十一月四号那天发布的样子，一年后也读得懂。换架构这种事，用 `gen` 单独标，比硬塞进 `MAJOR` 更清楚。
