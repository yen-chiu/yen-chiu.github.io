## 先看事实：三代站点

版本号不是凭空定的，先看仓库里真正发生了什么（截至 2026-11-19）：

| 代次 | 站点 | 从我的第一次提交算起 | 次数 |
| --- | --- | --- | --- |
| G1 | blog-v1 · Jekyll/huxpro（存档） | 2023-03-12 起 | 159 |
| G2 | yenchiu.com · Jekyll/Chirpy | 2023-10-17 起 | 660 |
| G3 | 新站 · Astro/Iris（预览） | 2026-11-17 起 | 56 |

三个仓库都自带别人的历史：G1 是 2017-02-10 qiubaiying 拉起的 BY Blog，2019 年交给 klovien（Globi Walker），到自己接手前共 391 次；G2 是 2019-09-30 Cotes Chung 拉起的 Chirpy（1,195 次模板与上游提交）；G3 是 2024-07-26 CWorld 拉起的 iris（593 次）。**这些不算站点的历史**——站点从「第一次以本人身份提交」那天才算开张，所以计数从那天起算。

子站：Manual 168 次（2024-11-21 起，模板作者另有 641 次）、Chat 114 次（2024-11-17 起）、Folio 4 次（2026-11-18 起）。

## 标准里怎么选

- [Semantic Versioning 2.0.0](https://semver.org/lang/zh-CN/)：`MAJOR.MINOR.PATCH`，前提是「有对外 API，且不兼容的改动能被消费者感知」。博客没有 API 消费者，`MAJOR` 只能靠人拍脑袋定义——G2 时代从 `v2.0` 走到 `v7.6.0`，回看时说不清 `v5` 到底「破坏」了什么。
- [Calendar Versioning](https://calver.org/)：用日期当版本，适合「持续交付、读者只关心新旧」的产物。站点每天在改，日期天然可比、可查。
- [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)：不规定编号，只规定**条目怎么写**——按 新增 / 调整 / 修复 / 移除 / 弃用 / 安全 分类。

本站 = 代次 + 日期编号，条目写法对齐 Keep a Changelog。

## 版本号：`v代次.日期`

- 格式 **`v3.2026.11.19`** = 第 3 代 · 2026 年 11 月 19 日。旧号段的 `v2.0`–`v7.6.0` 是随手取的，**不参与编号，也不必避让**。
- 仓库打 tag 用连字符形式 `v3.2026-11-19`，页面上显示点分形式。
- **一天最多一个版本**：当天改多少处，都收进这一条的 `items` 里逐项列出；同一天还真要再发第二次，末尾加 `.1`。
- 日期取「这一天最后一次真实提交」的日期（`Asia/Shanghai`），跨零点记在提交发生的那天。

## 按代次收拢

日志页不再是二十年一条时间线，而是每一代一个可展开的分组：G3 默认展开（正在用的），G1/G2 折起来备查。版本号里的代次前缀和分组用的是同一个 `gen` 字段，不会对不上。

| gen | 含义 | 时间 |
| --- | --- | --- |
| 1 | blog-v1（Jekyll · huxpro） | 2023-03 – 2023-10 |
| 2 | yenchiu.com（Jekyll · Chirpy） | 2023-10 – 2026-11 |
| 3 | 新站（Astro · Iris） | 2026-11 – 现在 |

换架构、换域名、换新站都只是 `gen +1`，日期照常往下走——「哪一天」和「哪一代」是两个维度。

## 代内再按站点分栏

同一天主站和子站都在改，混在一条里会看不清是谁动了什么。所以每条记录还带一个 `site`，代内再分栏：

| `site` | 中文 | 仓库 |
| --- | --- | --- |
| `main` | 主站 | `yen-chiu/yen-chiu-astro` / `yen-chiu.github.io`（含写作台） |
| `chat` | 聊天子站 | `yen-chiu/Chat`，挂在 `/chat/` |
| `manual` | 文档库 | `yen-chiu/WendellManual` → `yen-chiu/folio`（同一座站的两套架构） |

**子站换代际不算新代次**：文档库从 WendellManual 的 Jekyll 换成 Folio 的 Astro Starlight，站点还是那座站、`site` 还是 `manual`，只是条目里写清「从什么换到什么」。主站换架构才是 `gen +1`——因为那换的是博客本身，子站换架构只是它自己的一次大改。

一天里主站和聊天子站各改了一处，就是两条记录、同一个 `v3.2026.11.19`——版本号是「这一代这一天」，站点是分栏依据，两者不互相顶替。`scope`（主站 / 子站 / 写作台）是条目级的更细标注，和 `site` 不冲突。

## 改动方式 + 改动类别

每条先标**改动方式**（做了什么动作），再标**类别**（改的是哪块），两者搭配才说得清一件事：

| `change` | 中文 | 什么时候用 |
| --- | --- | --- |
| `added` | 新增 | 新功能、新页面、新入口 |
| `changed` | 调整 | 改了既有行为或结构 |
| `fixed` | 修复 | 修 bug、修错字级问题 |
| `improved` | 优化 | 没改行为，但更快、更小、更顺手 |
| `removed` | 移除 | 删掉功能或文件 |
| `deprecated` | 弃用 | 还能用，但准备下掉 |
| `security` | 安全 | 修漏洞、收紧权限 |
| `planned` | 计划 | 只出现在「在途改动」里 |

| `area` | 中文 |
| --- | --- |
| `feature` | 功能 |
| `style` | 样式 |
| `infra` | 基建（构建、部署、体积、迁移） |
| `docs` | 文档与规则 |

`scope` 是可选的作用范围（主站 / 子站 / 写作台），用来区分同一代里不同站点。

## 未发布

还没上线的改动放 `status: "unreleased"` 的条目里，页面上单独一块「在途改动」，用虚线框和「计划」标区分。发布那天整块搬进当天的版本，`status` 去掉即可。

## 一条记录长这样

```json
{
  "gen": 3,
  "date": "2026-11-19",
  "title": "更新日志独立成页，版本号定为「代次.日期」",
  "summary": "一句话说清这一天做了什么",
  "items": [
    {
      "change": "added",
      "area": "feature",
      "scope": "主站",
      "title": "更新日志独立成页",
      "note": "一句细节，列表里单行省略，悬停看全文"
    }
  ]
}
```

## 流程

1. 改完并提交站点改动；
2. 抄草稿：`node scripts/changelog-draft.mjs --repo . --since 2026-11-19 --gen 3 --site main`，把输出的 `items` 粘进来（跨仓库时换 `--repo` 和 `--site`，模板作者的历史记得用 `--author` 过滤）；
3. 写标题和一句话摘要，确认 `date` 是这次最后一次提交的日期；当天已有版本就追加 `items`，没有就新建一条；还没发布的先塞进「在途改动」；
4. `npm run build`，确认 `/changelog` 的分组、分栏和关于页最近三条都正常；
5. 提交信息用 `docs(changelog): v3.2026.11.19 一句话`；
6. **发布即打 tag**：`git tag v3.2026-11-19 && git push origin v3.2026-11-19`。日期版本最大好处就是能反查——一年后 `git show v3.2026-11-19` 就是那天发布的样子，不用翻提交。
